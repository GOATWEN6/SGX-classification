# SGX 分类与归纳实验说明

本文说明当前实验到底在测什么、为什么会停止，以及以后如何安全地换成真实家庭照片。它只描述当前 Stage A 分类链路，不把合成数据、真实 API 探索和真实家庭效果混成一个结论。

## 当前实验测什么

一次实验不是“把照片发给模型看一下”，而是一个有边界的可复现批次：固定照片清单、固定文字证据、固定模型版本、固定 Prompt 版本、固定预算和固定真值。任何一个批次都要留下输入哈希、审批引用、原始响应、用量账本和报告。

当前链路按下面顺序执行：

1. **准备清单**：每张图有 `photoId`、作用域、版本、来源引用、字节 SHA-256、MIME、caption 和可选的用户文字/final ASR 证据；另有独立 `truth.json`。
2. **离线预检**：检查图片哈希、真值哈希、主体和家庭作用域、事件分组是否泄漏、模型/价格是否仍有效、预估请求和费用是否在上限内。预检不读密钥、不联网。
3. **审批绑定**：审批文件绑定清单字节哈希、模型、准确照片集、费用/请求上限、有效期和人物匹配开关。密钥不写进审批文件。
4. **发送 Provider 请求**：服务端 Prompt 将图片、用户原文和 final ASR 作为独立证据发送；模型只产生候选观察，不产生用户已确认事实。
5. **严格解析**：先检查模型版本、结束原因、usage 和 JSON，再检查 `observations`/`relations` Schema，最后检查证据来源、未知 facet、冲突、时间精度和作用域。
6. **生成组织候选**：通过的 observation 才能进入事件候选、人物候选和相册 Story/Event 组织；候选状态仍是 `proposed` 或 `needs_review`，不会直接写入长期 Memory。
7. **记录和停止**：每次调用记录实际 usage 和保守预留。遇到截断、非法字段、模型版本变化、预算超限、授权变化或超时，当前批次停止，未处理照片保留在分母中，不通过重试隐藏失败。

## 为什么最近几轮会报 `INVALID_OUTPUT`

模型已经真实返回，但它的自然语言理解和工程字段形状不是一回事。最近的错误依次是：输出被截断；一张照片被拆成多个 observation；顶层键写成 `extract/relate`；现在又是 `bbox/timeText/placeText/eventText/sceneText/evidence` 等字段与 Schema 不一致。严格拒收是有意设计的，否则错误候选会进入相册、Memory 或后续访谈。

`STAGE_A_EXIT_2` 是批处理包装脚本把“受控停止”传递给外层 shell；它不等于进程崩溃。费用中的保守预留也不等于供应商最终账单，真实 usage 和账本需要分开看。

2026-09-25 的第六轮再次说明了这个边界：模型返回的是合法 JSON，顶层 `observations`、单照片单 observation 和主要字段都已经正确，但把文档里的可选字段写法 `canonical?` 原样当成了字段名。Schema 因额外字段拒收。即使删除这个字段，输出中的视觉文字 `生日快乐` 仍被错误放进 `mentions`，会在下一层语义校验触发 `MENTION_WITHOUT_TEXT`；同时它漏掉了用户文字与视觉生日线索之间的 `event` 冲突。

这不是 endpoint、密钥或模型没有被真实调用。原始响应中的供应商响应 ID、固定模型版本、`finish_reason=stop` 和实际 usage 都证明调用发生过。反复出现的原因是当前图片调用使用 `json_object`：它只保证输出是 JSON，不保证键名、类型和层级稳定。阿里云官方也明确说明，多模态输入使用 `json_schema` 时会自动降级为 `json_object`，Schema 约束不生效：<https://help.aliyun.com/zh/model-studio/qwen-structured-output>。

## 三类错误怎样区分

|类别|典型错误|是否发生付费调用|处理方法|
|---|---|---:|---|
|执行保护|`APPROVAL_EXPIRED`、`OUTPUT_DIRECTORY_EXISTS`|否|更新准确授权；每轮使用新的结果目录|
|Provider/契约|`OUTPUT_TRUNCATED`、`INVALID_OUTPUT`、`MODEL_VERSION_MISMATCH`|可能发生|看 result 中的 `diagnostic.phase/issues` 和原始响应，先离线修复再开新批次|
|语义质量|漏冲突、误判事件、未知项错误、错合并|是|进入固定真值评分；Prompt、规则或阈值只在探索集修改|

结果目录已存在时拒绝覆盖，是实验可追溯性的保护，不应删除旧目录后原名重跑。使用带轮次和日期的新目录，例如 `/private/tmp/sgx-d4-qwen37-run-r7-20260925`。现在 CLI 会直接返回 `OUTPUT_DIRECTORY_EXISTS`，不再把它显示成 Node `EEXIST` 堆栈。

## 固定排查顺序

每次失败按同一顺序检查，避免从日志最后一行猜原因：

1. 看终端首个稳定错误码；`STAGE_A_EXIT_*` 只曾是外层包装结果，不是根因。
2. 看 `REPORT.md` 的“工程诊断”，确认失败阶段、字段路径、Zod 错误码和非法键。
3. 看 `result-<taskId>.json` 的 `errors[].diagnostic`，这是机器可读的同一诊断。
4. 只有需要核对模型原话时才看 `provider-responses.jsonl`；不要把整段原始 JSON 当成最终评测结果。
5. 对历史原始响应做离线 Schema/语义复盘，列完全部阻断项，再改 Prompt 或适配器。
6. 运行 typecheck、密钥扫描和完整分类回归；全部通过后才准备新的 manifest、approval 和新结果目录。
7. 新一轮先跑一张契约探针。探针通过后才扩大到多图和关系阶段；失败立即停止，保持 0 自动重试。

当前实现会把安全诊断写入结果和 Markdown 报告，只保留字段路径、错误码、预期类型和非法键名，不回显字段值、密钥、请求头或任意上游错误正文。

真实 API 密钥可通过 `scripts/classification-keychain.zsh setup` 一次性保存到当前 macOS 用户的 Keychain。后续实验使用 `scripts/classification-keychain.zsh eval ...` 读取，避免每轮重复输入。脚本只把密钥注入当前评测子进程，不打印密钥，也不写入 `.env`、Git、approval、结果目录或报告。更换或撤销密钥时，应在 Keychain 中更新或删除服务 `com.freewizardwu.ai-frame.sgx-d4-api-key`，不在聊天中发送明文。

## 如何降低再次发生的概率

短期继续采用“多模态抽取 + 本地严格校验”，因为第六轮已经接近契约通过；Prompt 版本已升级为 `sgx-five-facets.3`，移除了 `canonical?`、`instanceHint?`、`evidenceId?` 这类会被模型照抄的伪 JSON 写法，并明确 `mentions` 只允许来自 caption、user_text、final_asr 的人物名称或关系。

如果后续仍频繁出现字段漂移，应停止逐字段修 Prompt，改为显式两阶段：第一阶段让视觉模型产生有证据的抽取草稿；第二阶段用**纯文本**调用和严格 `json_schema` 把草稿规范化为正式 Observation。第二阶段是独立模型请求，必须单独计入请求数、Token、费用、授权和日志，不能伪装成“自动重试”。在当前 10 请求上限下，5 张图仅“视觉抽取 + 规范化”就会用满 10 次，因此进入该方案前要先改预算模型和评测清单。

2026-09-25 的 C014 单图探针已经通过工程契约，说明当前不需要立即引入第二次规范化 API 调用。新的主要问题是自由描述与产品分类词表不一致：模型输出“室内家庭聚餐”一类完整短语，固定真值按“室内”“庆典”等受控标签计分。`sgx-five-facets.4` 先要求模型直接使用 P0 受控事件/场景标签；若小批量响应仍频繁偏离词表，再实现独立、可版本化的归一化层。

unknown 和 conflict 的评分范围目前跟随 task 的 `evaluation.facets`。只启用 scene 时，event conflict 会进入产品 `reviewItems`，但不会进入该任务的自动 conflict 分数。设计实验时必须显式启用需要评价的 facet，不能用 metrics 中的 0/0 推断模型没有发现冲突。

模型输出中的确定性表示差异在本地归一化：例如 `2005年` 转为 year 值 `2005`，`2026年9月7日` 转为 date 值 `2026-09-07`；`unknownFacets` 由已通过结构校验的 people/mentions、times、places、events、scenes 数组自动计算。该层只改变格式和派生空值状态，不生成新事实、不添加冲突，也不替代模型和人工对照片语义的判断。

## 真实照片应该怎么准备

真实照片不能直接替换 synthetic-v2 的文件。应建立一个新的真实数据批次，并在调用前完成授权和人工真值。第一批建议 20–30 张，分成 6–10 个独立事件；确认流程稳定后，再扩展到 30–50 张。每个事件至少保留一张信息明确的照片和一张信息不完整或有冲突的照片。

建议覆盖：家庭团聚、生日或婚礼、旅行、同学/战友聚会、退休生活、日常做饭或养花、老照片翻拍、只有风景/物品的照片，以及一两张模糊或信息不足的拒判样本。近重复照片和同一事件照片必须放在同一个数据分区，不能把一张事件的相似副本放到探索集、另一张放到最终验收集。

每张真实照片至少需要这些信息：

- 原始文件和拍摄来源；
- 用户自己写的说明，允许为空；
- 如果有语音，提供最终 ASR 文本，不能把部分 ASR 当最终事实；
- 人工确认的事件、时间、地点、场景、冲突和未知项；
- 是否允许外发给指定模型服务商；
- 是否允许人物框检测或人物匹配。默认关闭人物匹配。

当前 Provider 的实验输入上限是单张图片 1 MiB。手机原图若超过上限，不能在后台偷偷压缩后当成原图；应生成有记录的派生测试文件，保存原图哈希、派生图哈希、缩放参数和用途。模型实际看到的是派生文件，报告中必须明确这一点。当前仓库还没有“真实照片目录 → manifest/truth”自动准备器，因此真实照片批次开始前需要先补这个准备步骤，或者按现有 Manifest/Truth 契约人工生成并审核。

## 真值怎么写

真值由用户或独立审阅者在模型调用前冻结。真值只记录当时允许使用的证据，不因为模型输出而事后改答案。每张图需要标记：

- 事件是否存在，以及同一事件的 `eventInstance`；
- 时间是明确年份、年代、相对时间还是未知；
- 地点和场景是否有文字/EXIF/可见依据；
- 哪些 facet 应拒判；
- 哪些 facet 存在冲突；
- 人物指标是否关闭，或是否有独立的人物框与授权。

用户明确说“这是周末聚餐，不是生日”时，真值应保留 `event` 冲突，而不是让算法替用户选生日或聚餐其中一个。用户自己指定的亲属关系可以作为独立来源保存；模型只能提出“可能相关”，不能把上传者自动认定为照片主体。

## 真实照片实验的三个阶段

**阶段 A：接口和契约通过。** 目标是所有模型响应都能被严格 Schema 和语义校验接受；不评价准确率。任何一张照片的非法字段都要修复 Prompt、适配器或模型设置后重新开一个有 provenance 的批次。

**阶段 B：探索集语义评估。** 固定 Prompt、模型和阈值，对时间、地点、事件、场景、未知/冲突和同事件关系做固定分母评分。人物身份和跨年龄人脸匹配另开实验，不能从普通 VLM 观察结果推断。

**阶段 C：独立保留集。** 保留集在 Prompt 和规则冻结后才调用；探索集中的错误不能反过来修改保留集真值。只有这一阶段通过，才可以讨论是否进入全栈联调或小规模 shadow/pilot。

## 当前结束标准

当前这条线的近期结束标准是：一次新的固定批次中，真实响应通过完整 `ObservationSchema` 和 `validateObservation`，不再因为字段形状停止；随后至少完成一个探索批次的固定分母报告。它仍然不能称为真实家庭准确率。

真实家庭测试的结束标准还要增加：材料外发授权、人物用途边界、独立真值、事件分区、原图/派生图 provenance、未知/冲突统计、失败样本和供应商费用账单核对。没有这些证据，只能称为工程探索，不能称为产品达标。
