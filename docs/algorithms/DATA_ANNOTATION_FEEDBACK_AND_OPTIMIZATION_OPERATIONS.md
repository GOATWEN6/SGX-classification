# 数据标注、用户反馈与算法调优协作手册

> 文档状态：`draft_for_owner_review`
> 版本：`0.1.0`
> 日期：2026-09-04
> 主要读者：项目负责人、算法、产品、数据标注、用户研究、测试与运营人员

## 1. 结论：当前阶段需要怎样的团队

当前建议采用“1 名负责人 + 1 名主标注人员 + 1 名兼职辅助人员”的最小配置：

| 角色 | 建议投入 | 核心责任 |
|---|---:|---|
| 算法与产品负责人 | 由项目负责人承担，每周约 2–4 小时决策时间 | 定义目标、冻结规范、裁决争议、批准实验和发布；不做日常标注 |
| 数据标注与质量专员 | 0.8–1.0 FTE，pilot 期间为核心岗位 | 主标注、数据质量、版本、错误分析、golden set 生产和文档维护 |
| 用户研究与独立复核协作员 | 0.2–0.4 FTE，约每周 8–16 小时 | 盲法复核、老人/家庭体验反馈、pilot 协调、问题登记和回访 |

这里的“两个人”不是各自随意标注一半：

- 主标注专员负责稳定地产出标注结果。
- 辅助协作员负责独立检查和收集用户反馈，避免同一个人既生产答案又证明自己正确。
- 项目负责人只裁决少数规则争议，不承担大量重复工作。

在预算非常有限时，辅助岗位可以兼职；但“关键样本由第二个人独立复核”不能完全取消。AI 可以预处理、推荐标签和做一致性扫描，但不能替代正式人类 gold 标注和独立复核。

## 2. 为什么当前规模适合这个配置

已确认的近期范围是：

- 约 10–30 位老人。
- 每位老人 4 周内通常提供 20–50 张照片，少量超过 50 张。
- 每位老人计划完成 3–5 次访谈。

仅照片部分，典型规模约为 200–1,500 张；还会产生文字说明和访谈转写。第一轮校准后，若一张照片的基础多维标注平均需要 3–6 分钟，照片工作量约为 10–150 小时，实际时间还会受到人物确认、老照片质量、转写长度和争议样本影响。因此一名核心标注专员可以承担当前 pilot，但需要兼职复核和用户研究协作，不能把所有工作压给项目负责人。

以上是人力规划估算，不是已测量工时。正式排班以首轮 30–50 个素材的计时校准结果为准。

## 3. 角色一：数据标注与质量专员

### 3.1 岗位使命

把用户授权的原始图片、文字和语音转写转换成一致、可追溯、可复核的数据资产，并把算法失败整理成团队能够行动的问题。该岗位不是普通“点标签”人员，而是算法数据质量的第一责任人。

### 3.2 开始标注前的工作

1. 学习产品目标、隐私边界、五算法定义和当前 P0 SPEC。
2. 与算法负责人共同维护 taxonomy、字段解释、正例、反例和边界例。
3. 用合成或脱敏素材完成培训和资格校准。
4. 检查标注工具能否记录 Evidence ID、support span/region、版本和不确定状态。
5. 先对 30–50 个素材进行校准标注，记录耗时和争议；校准样本不进入最终 held-out test。
6. 在规范冻结前，不批量启动正式标注。

### 3.3 数据接收与质量检查

- 核验批次 ID、数据版本、授权状态和用途范围。
- 确认每条 Evidence 已指定当前老人 `subjectId`，但不猜测群像中其他人的真实身份。
- 检查图片可读性、方向、重复/近重复、EXIF 状态和明显损坏。
- 检查语音转写是否有低 ASR 置信度、说话人混淆、缺失片段或时间戳异常。
- 发现跨家庭混入、授权缺失、删除状态或主体错误时立即隔离，不继续标注。
- 不在个人电脑、聊天软件或飞书文档中复制原始隐私素材。

### 3.4 正式标注工作

按 `Evidence × facet` 记录：

- 时间：具体日期、年份、年代、区间、相对时间和人生阶段。
- 地点：原始表达与规范化层级；不根据模糊景物猜精确地址。
- 人物：用户明确身份、匿名人物簇、画面区域和关系候选。
- 事件：求学、工作、婚礼、生日、旅行、退休、家庭聚会等。
- 场景、主题、内容类型和质量问题。
- 文本中的原子事实及其证据跨度。
- `uncertain`、`not_applicable` 和 `conflicted` 状态。
- 隐私/敏感线索只作治理标记，不替用户决定分享范围。

每条标注必须能回到具体图片区域、转写片段或文字跨度。没有证据就不标；不能判断就明确标记不确定，不能靠常识补齐老人的人生事实。

### 3.5 日常质量控制

- 每批完成后自查漏标、互斥冲突、越界标签和格式错误。
- 检查标签分布、未知率、冲突率、异常高频标签和标注耗时。
- 确保同一老人、家庭、图片变体、转写和摘要不跨 train/dev/test。
- 保存 point-in-time 输入快照，避免未来确认结果泄漏给更早任务。
- 维护批次、规范、taxonomy、工具和标注者版本。
- 对敏感、冲突、低置信和新类型样本全部送独立复核。
- 随机抽取至少 20% 的普通样本做双标。

### 3.6 错误分析和算法反馈

主标注专员每周把失败划分为可行动类型：

| 错误类型 | 示例 | 主要处理方 |
|---|---|---|
| 数据质量 | 图片模糊、转写错误、EXIF 缺失 | 采集/ASR/客户端 |
| 标注规范 | “家庭聚会”与“节庆”边界不清 | 标注与算法负责人 |
| taxonomy | 缺少适合真实用户的新类别 | 产品、内容、算法 |
| 模型错误 | 有证据但分类错误或漏标 | 算法研发 |
| 融合错误 | EXIF 与用户描述冲突时错误覆盖 | 算法与后端 |
| 权限错误 | 越权使用或展示了标签 | 后端、安全、产品 |
| 体验错误 | 标签正确但用户看不懂或难以确认 | 产品与用户研究 |

不能把所有问题都归因于“模型不够好”。很多问题应通过采集、schema、taxonomy、权限或交互修复。

### 3.7 必须交付的产物

- 标注规范及版本变更记录。
- taxonomy 与标签映射表。
- 已标注批次 manifest。
- 数据质量和排除样本报告。
- 双标一致性和争议清单。
- 冻结 golden set 数据卡。
- 每周错误分析和回归样本建议。
- 删除、撤回和数据集 exclusion 记录。

### 3.8 明确禁止事项

- 不擅自修改原始照片、原声或用户文字。
- 不猜测人物身份、家庭关系、疾病、认知状态或真实动机。
- 不为了提高完成量隐藏无法判断和失败样本。
- 不查看测试集结果后修改 gold 以迎合模型。
- 不把模型预标直接当作人工答案。
- 不把产品数据复制到个人工具或未经批准的模型服务。
- 不独自批准算法上线或发表科学结论。

## 4. 角色二：用户研究与独立复核协作员

### 4.1 岗位使命

帮助负责人运行 4 周 pilot，独立检查关键标注，并把老人和家庭的真实体验转化为结构化产品反馈。该角色既不是客服话术人员，也不是第二个随意标注者。

### 4.2 Pilot 运营工作

- 按批准名单安排入组、设备/账号准备和使用说明。
- 确认产品使用 consent 与科研 consent 分开，不替老人作决定。
- 记录设备、网络、图片数量、访谈完成和异常情况。
- 帮助解决上传、麦克风、字幕、主体切换和返回路径问题。
- 提醒但不强迫用户完成任务；记录退出、跳过和失访。
- 对隐私、安全、错误记忆和删除问题使用高优先级升级流程。

### 4.3 独立复核工作

- 对随机至少 20% 的普通样本，以及全部敏感、冲突、低置信、新类别样本独立标注。
- 制作 gold 时看不到待评模型输出和主标注员答案。
- 复核完成后再进行差异比较，不在标注过程中相互提示。
- 区分“标注员疏漏、规范歧义、证据本身不足和模型错误”。
- 输出一致性统计和争议理由，不以个人感觉直接覆盖主标注。
- 对无法达成一致的定义问题提交负责人裁决。

用户访谈与盲法复核由同一兼职人员承担时，必须使用分开的任务队列：做 gold 的样本不能提前向其展示模型结果、用户对模型标签的确认结果或主标注答案。

### 4.4 用户体验研究工作

- 观察老人是否能独立完成进入、上传、对话、确认、跳过和退出。
- 询问标签是否看得懂、是否准确、是否让用户感到被监视或被冒犯。
- 收集老人和家庭各自的体验，不能只听家属替老人评价。
- 记录完成任务所需帮助、操作次数、等待、失败恢复和疲劳。
- 把自由反馈转换成问题分类，但保留必要原话和上下文引用。
- 不暗示用户给正面评价，不把高使用时长直接解释为满意。

### 4.5 必须交付的产物

- 入组、退出和联系状态表，不包含无关敏感信息。
- 双标结果和一致性报告。
- 每周用户体验摘要及高优先级问题。
- 设备/网络/流程问题清单。
- 隐私、安全和不良体验事件记录。
- 第 4 周总结访谈和建议优先级。

### 4.6 明确禁止事项

- 不把用户反馈改写成算法事实或科研标签。
- 不诱导老人继续讲不愿意讲的内容。
- 不代用户确认个人 Memory、授权分享或加入研究。
- 不为了留存率淡化退出、投诉和失败。
- 不把研究问题混入普通产品服务而不告知用户。
- 不在飞书群或普通表格中存放完整原声、照片或敏感对话。

## 5. 项目负责人应该负责什么

项目负责人不需要做日常标注，但必须承担不能外包的决策：

1. 定义本轮用户价值、算法目标和明确不做什么。
2. 批准 taxonomy、标注规范、golden set 形成规则和数据用途。
3. 决定产品与科研边界、预算、外部模型和数据外发范围。
4. 每周处理少量无法由规范解决的争议，不逐条重做标注。
5. 审批算法变更、实验设计、feature flag、pilot 和发布。
6. 保证失败分母、反例、隐私事件和停止条件被如实报告。
7. 决定产品主线优先级，不让科研指标损害老人体验。
8. 对任何学术、医疗或社会价值主张承担最终审核责任。

建议负责人固定每周一次 45–60 分钟质量与算法评审，而不是被大量即时问题打断。只有 P0 安全或隐私事件需要立即升级。

## 6. 从算法设计到产品反馈的完整闭环

```text
产品问题与用户价值
        ↓
定义算法任务、输入、输出、不做什么
        ↓
冻结 schema、taxonomy、标注规范和指标
        ↓
小批量校准标注（30–50 个素材）
        ↓
合成 fixtures / baseline / contract tests
        ↓
经授权真实数据 → 主标注 → 盲法复核 → 争议裁决
        ↓
冻结 dev/test 与 golden set
        ↓
离线训练或调优 → 锁定版本 → held-out test
        ↓
feature flag / shadow mode / 小范围产品 pilot
        ↓
行为数据 + 明确反馈 + 体验访谈 + 安全事件
        ↓
问题归因：数据 / 规范 / 模型 / 系统 / UX / 权限
        ↓
提出变更 → dev 验证 → 回归 → 新版本 → 再次 pilot
```

每一次循环都必须能回答：改了什么、为什么改、使用了哪些数据、哪些指标变好或变差、是否出现新伤害、怎样回滚。

### 6.1 算法与产品结合的四级发布方式

| 级别 | 产品行为 | 允许条件 |
|---|---|---|
| L0 离线 | 只在合成/冻结数据上运行，用户不可见 | schema、fixtures、baseline 和离线 harness |
| L1 Shadow | 对真实授权输入后台运行，但结果不影响用户 | 独立批准、权限/删除通过、完整监控 |
| L2 辅助建议 | 向少量用户展示候选，必须确认才能生效 | 离线 Gate、体验设计、feature flag、停止规则 |
| L3 产品默认能力 | 在批准范围内默认提供，仍可修改、关闭和回滚 | pilot 证明产品价值且安全指标达标 |

分类归纳在当前只获准进入使用合成数据的 L0。产品结合不是把模型 API 接上页面就完成，而是逐级验证错误是否可控、用户是否理解和能否退出。

## 7. 4 周用户反馈方案

### 7.1 收集四类反馈

| 类别 | 回答的问题 | 示例 |
|---|---|---|
| 任务结果 | 用户是否完成想做的事情 | 成功上传、完成分类确认、找到照片、结束访谈 |
| 行为反馈 | 哪里出现摩擦 | 修改、拒绝、跳过、重复点击、重试、退出、等待时间 |
| 明确体验 | 用户怎样感受 | 看得懂吗、觉得准吗、是否省力、是否疲劳、是否被冒犯 |
| 安全与隐私 | 是否产生伤害或失控 | 错误人物、虚假记忆、越权展示、删除失败、敏感内容误用 |

行为数据不自动代表态度。例如“没有修改标签”可能是标签正确，也可能是老人不会修改，因此必须与访谈和任务观察结合。

建议的最小产品事件名称：

```text
classification_result_viewed
classification_assertion_confirmed
classification_assertion_edited
classification_assertion_rejected
classification_assertion_skipped
classification_retry_requested
classification_feedback_submitted
content_trashed
content_restored
content_permanent_delete_requested
```

事件只记录必要 ID、版本、状态和耗时；照片、完整转写和自由反馈正文不进入普通埋点。

### 7.2 建议节奏

| 时间 | 活动 | 用户负担控制 |
|---|---|---|
| 第 0 天 | 入组、基本使用能力、授权、设备和网络基线 | 只收完成任务所需信息 |
| 每次分类确认后 | 1 个可跳过的轻反馈：“这些整理结果有帮助吗？” | 不要求长问卷，不阻塞退出 |
| 第 1 周 | 10–15 分钟短回访，重点看不会用和明显错误 | 老人和家属分别表达，不互相代答 |
| 第 2–3 周 | 以自然使用和问题支持为主；只对失败用户定向回访 | 避免每周重复打扰全部老人 |
| 第 4 周 | 20–30 分钟总结访谈和任务复测 | 允许随时暂停、跳过和退出 |

### 7.3 最小反馈字段

```yaml
feedback_id:
subject_id_or_research_pseudonym:
actor_type: elder | contributor | authorized_family
product_or_research_scope:
evidence_id:
job_id:
algorithm_version:
taxonomy_version:
feedback_source: behavior | one_tap | interview | support | incident
feedback_type: helpful | incorrect | missing | confusing | intrusive | privacy | failure
rating:
structured_reason:
free_text_ref:
occurred_at:
consent_ref:
```

自由文本和原声存放在受保护内容系统中；普通分析表只保存引用和结构化分类。

### 7.4 体验指标

- 独立完成率和需要帮助比例。
- 每条内容确认所需时间和操作数。
- 标签确认、编辑、拒绝和跳过比例。
- 错误人物、错误时间、错误地点和无依据标签率。
- 用户对“有帮助、容易理解、可以控制、愿意继续使用”的评分。
- 疲劳、被监视感、被冒犯感和隐私担忧。
- 删除、退出和错误恢复是否成功。
- 老人与家属评价不一致的比例和原因。

产品指标、算法离线指标和科研结论分别报告。体验改善不能自动证明算法科学有效，分类准确率提高也不自动证明用户更满意。

## 8. 算法调优流程

### 8.1 先归因，再决定是否改模型

每个问题进入统一 `ErrorCase`，依次判断：

1. 原始数据是否可用？
2. 标注是否一致、规范是否清楚？
3. taxonomy 是否覆盖真实用户表达？
4. 算法是否提取/归一/融合错误？
5. 后端是否使用了错误主体、权限、版本或缓存？
6. 结果虽然技术上正确，是否因表达或交互让老人难以理解？

只有第 4 类主要通过模型调优解决。其他问题分别进入采集、数据、后端、安全或产品 backlog。

### 8.2 调优优先级

按以下顺序处理：

1. P0：跨家庭泄漏、错误主体、删除复活、未经确认写入 Memory、敏感内容误用。
2. P1：高频错误、导致老人无法完成任务、明显增加确认负担的问题。
3. P2：低频长尾、轻微文案、模型覆盖率优化。

同级问题再比较：影响人数 × 发生频率 × 用户伤害/价值 ÷ 修复成本。不能只挑容易提高离线分数的错误。

### 8.3 每次算法变更必须包含

- 变更假设和目标错误类型。
- 新增数据来源和授权范围。
- 训练/dev/test 切分及 point-in-time 证明。
- baseline、ablation 和关键分组指标。
- 未改善和变差的指标。
- 新增回归 fixtures。
- 模型、prompt、taxonomy、代码和数据版本。
- shadow/feature flag、停止条件和回滚方法。

### 8.4 防止错误调优

- 不反复查看 held-out test 后继续改模型。
- 不把用户对模型候选的点击直接当成无偏 gold。
- 不让待评模型的输出回流成为自己的训练标签。
- 不删除失败、拒判和退出用户来美化指标。
- 不用一个总准确率掩盖人物、隐私或最差人群表现。
- 不因使用时长提高就声称老人更幸福或认知改善。
- 外部模型升级后必须作为新 provider version 重跑回归。

## 9. 两个执行岗位怎样协作

### 9.1 标准批次流程

```text
负责人冻结任务和规范
        ↓
主标注专员接收批次、质检、主标
        ↓
系统随机抽取 20% + 全部关键样本
        ↓
辅助协作员在盲法队列中独立复核
        ↓
系统生成差异，不直接覆盖
        ↓
两人按规范解决操作性分歧
        ↓
仍有定义争议 → 负责人裁决并更新规范版本
        ↓
重新校准受影响标签 → 冻结批次
```

### 9.2 RACI

| 工作 | 负责人 | 主标注专员 | 辅助协作员 | 算法/工程 |
|---|---|---|---|---|
| 定义用户目标和发布边界 | A/R | C | C | C |
| taxonomy/标注规范草拟 | A | R | C | C |
| 主标注和批次质检 | I | A/R | I | C |
| 独立盲法复核 | I | I | A/R | I |
| 规则争议裁决 | A/R | C | C | C |
| 用户入组和回访 | A | C | R | I |
| 算法开发和自动评测 | A | C | C | R |
| 隐私/安全事件处置 | A/R | C | R | R |
| 产品发布决定 | A/R | I | I | C |

`R` 为执行，`A` 为最终负责，`C` 为参与咨询，`I` 为知会。一项工作只能有清晰的最终负责人。

### 9.3 每周节奏

- 周一：冻结本周批次、版本和优先问题。
- 周二至周三：主标注、数据质检和用户问题支持。
- 周四：盲法复核、一致性统计和争议整理。
- 周五：45–60 分钟负责人评审，决定规范修订、算法 backlog 和下周实验。
- P0 隐私/安全问题：发现即停止相关处理并立即升级，不等周会。

## 10. 岗位考核不能只看“标了多少”

### 10.1 主标注专员

建议指标：

- 批次按时完成率和记录完整率。
- 关键字段、证据跨度和版本完整率。
- 双标一致性：关键 facet 原始一致率目标不低于 85%，Cohen's kappa 目标不低于 0.70；未达到时先修规范，不能惩罚性追量。
- 漏标、越权处理、数据泄漏和测试集污染事件。
- 错误分类是否能转化成可行动的工程问题。
- 删除和 exclusion 记录完整性。

### 10.2 辅助协作员

建议指标：

- 独立复核覆盖率和盲法执行完整性。
- 入组、回访、退出和问题状态记录完整率。
- 老人本人反馈覆盖，而非只有家属意见。
- 高优先级体验/隐私问题发现和升级时效。
- 自由反馈结构化后的可追溯率。
- 不以用户留存或正面评分作为个人单一 KPI，避免诱导反馈。

### 10.3 项目负责人

建议自检：

- 争议是否在约定时限内得到明确决策。
- 是否控制 taxonomy 和实验范围频繁变化。
- 是否保留失败分母和反例。
- 是否因产品进度跳过权限、删除或测试门禁。
- 是否把 pilot、工程验证和科学结论正确分层。

## 11. 何时需要扩充为三个执行岗位

当前两个执行角色足够启动。如果出现以下任一情况，建议把“用户研究”和“独立数据 QA”拆成两个不同岗位：

- 持续服务超过 30 位老人，或同期素材显著超过 1,500 张照片。
- 方言、长音频、多人照片或敏感内容使复核工作明显增加。
- 用户研究需要开展正式随机实验或多机构纵向研究。
- 兼职协作员因看过模型/用户反馈而无法保持 gold 盲法。
- 隐私、安全或临床合作要求更严格的职责隔离。

扩充后的岗位分别为：数据标注专员、独立数据 QA、用户研究/Pilot 运营。项目负责人仍不承担日常标注。

## 12. 招聘画像

### 12.1 数据标注与质量专员

优先能力：

- 细致、稳定，能严格按规范工作并记录不确定性。
- 能理解中文口述、家庭关系、时间地点和老照片语境。
- 熟悉表格或标注工具；愿意学习 JSON、版本号和基础数据概念。
- 有数据标注、质检、档案、口述史、语言学或用户研究经验更佳。
- 尊重老人隐私，不凭常识替用户补写人生事实。
- 能从重复错误中总结规则，而不只是机械操作。

面试可使用脱敏/合成样本完成 60–90 分钟试标，观察证据引用、边界判断、争议记录和自查能力，而不是只考速度。

### 12.2 用户研究与独立复核协作员

优先能力：

- 能耐心、非诱导地与老人沟通。
- 能区分老人本人、家属和系统三方视角。
- 有用户访谈、社区服务、养老服务、社会工作、心理/教育研究或 QA 经验更佳。
- 能执行盲法复核，不因知道产品目标而迎合结果。
- 能处理设备和流程问题，但不越权解释医疗或认知结论。
- 遇到隐私、安全和不良体验时知道立即升级。

## 13. 本轮待负责人确认

1. 是否采用“主标注专员全职/核心投入 + 辅助协作员兼职”的配置。
2. 辅助协作员是否同时承担用户回访和盲法复核；若承担，是否接受分队列隔离要求。
3. 用户回访由社区/机构协助安排，还是由项目团队直接安排。
4. 原始隐私数据使用什么受控标注工具；飞书知识库只存规范和汇总，不存原始素材。
5. 首轮 30–50 个素材校准完成后，再确认真实每条标注工时和排班。
